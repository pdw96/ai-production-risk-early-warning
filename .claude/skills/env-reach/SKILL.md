# 무엇이 닿는가 — 그리고 막혔을 때 무엇을 의심하는가

> **막힘은 규칙이 아니라 측정이다.** 「한 번 막혔으니 안전하다」에 기대어 보호를
> 설계하지 않는다. 아래 값에는 전부 **잰 날짜**가 붙어 있고, 어긋나면 **다시 잰
> 값이 맞다.**

**날짜가 붙는 자리는 둘이다** — 표는 **행마다**, 표가 아닌 절은 **절 끝의 `실측`
줄**이다. 날짜 없는 단정은 남기지 않는다. 남기면 다음 사람이 **언제 다시 재야
하는지**를 알 수 없고, 그 사이에 열린 길을 계속 사람에게 넘긴다.

## 못 나간 호출은 셋으로 갈린다 — 문구로 가른다

| 무엇 | 무엇으로 식별하나 | 어디서 막혔나 |
| --- | --- | --- |
| **분류기** | 문구가 **정확히** `Permission for this action was denied by the Claude Code auto mode classifier` | **요청이 나가지도 않았다** |
| **프록시·권한** | HTTP 코드가 있다 — `403 Resource not accessible by integration` 등 | 요청은 나갔고 GitHub 이나 프록시가 거절했다. **5xx 는 예외다 — 아래를 본다** |
| **전송 실패** | 코드도 없고 위 문구도 아니다 — DNS·TLS·프록시 연결·타임아웃·연결 끊김 | **아무도 거절하지 않았다.** 닿지 못했을 뿐이다 |

> **분류기는 그 문구로 알아본다. 「HTTP 코드가 없다」로 알아보지 않는다.**

셋째 줄이 그 이유다. 전송 실패도 코드가 없는데, 그것을 분류기로 읽으면 **아래의
「멈추고 보고한다」가 걸려 복구 가능한 일을 세운다.**

**다만 전송 실패를 전부 다시 걸지는 않는다 — 둘로 갈린다.**

| 어느 쪽 | 어떤 실패 | 무엇을 한다 |
| --- | --- | --- |
| **발송 전이 확실** | DNS 실패 · TLS 핸드셰이크 실패 · 프록시 연결 거부 | 요청이 나가지 않았다. **그대로 다시 건다** |
| **배달 불명** | 보낸 뒤 타임아웃 · 전송 중 연결 끊김 · **게이트웨이 5xx(`502`·`504`)** | **GitHub 이 이미 처리했을 수 있다.** 다시 걸기 전에 **원격 상태를 읽어 확인**하거나, 결과가 같은 호출로 바꾼다 |

**`502`·`504` 가 여기 있는 이유** — 코드가 있어도 **거절이 아니다.** 프록시가 POST 를
GitHub 에 넘기고 **응답만 잃어도** 그 코드가 온다. 「코드가 있으면 거절」로 읽으면
**이 둘이 재시도 방지 경로에서 빠진다.** 실제로 이 세션에서 `draft → ready` 가
502 로 세 번 떨어졌다(2026-09-13).

**배달 불명을 그냥 다시 걸면 이슈·코멘트·PR 이 둘씩 생긴다** — 이 문서가 지키려는
바로 그 되돌릴 수 없는 것들이다. **어느 쪽인지 모르면 배달 불명으로 읽는다.**

어느 쪽이든 되풀이되면 프록시 상태를 본다(`$HTTPS_PROXY/__agentproxy/status`).

셋을 섞으면 엉뚱한 데를 고친다. 분류기는 **권한 시스템 다음에 오는 2차 관문**이라
`permissions.allow` 로 우회되지 않는다.

**분류기는 도구·세션마다 갈리고, 같은 호출이 한 번은 막히고 한 번은 통과한다.**
그러므로:

- **분류기 거부면 재시도 루프를 돌리지 말고 그 자리에서 멈추고 보고한다.** 되돌릴 수
  없는 것(이슈 번호 등)을 태우는 것을 그 규칙이 막았다.
- **우회를 만들지 않는다.** 특히 막힌 것이 **사람에게 남겨 둔 그 일**이면, 다른
  도구로 돌리는 것은 규율을 지우는 것이다.
- **클라우드에서 막힌 일을 로컬 세션에 대신 시키지 않는다** — 권한 세탁이다.
  할 일은 **명령지를 짜 드리는 것**이다.

<sub>실측 2026-09-09 ~ 2026-09-14 — 두 문구 모두 이 기간에 여러 번 받았다.</sub>

## 자격증명은 호출자가 넣은 값이 아니다 — 무엇인지는 헤더로 정해지지 않는다

`GET /user` 에서 `X-OAuth-Scopes` 가 **비어 있고** rate limit 이 **15,000** 이었다
<sub>(실측 2026-09-14)</sub>. **여기서 「그러니 PAT 이 아니라 앱 설치 토큰이다」로
건너뛰지 않는다** — 이 두 값은 자격증명의 종류를 **유일하게 가리키지 않는다.**

<sub>**앞 판은 그렇게 건너뛰었고 절 제목까지 그렇게 달았다.** 그런데 이 문서가 뒤에
적은 둘이 그 단정을 흔든다 — **잰 저장소 범위 세 호출**은 `X-OAuth-Scopes` 가 **아예
없고** 한도가 **5000** 이었고(실측 2026-09-15 · 어느 셋인지는 아래 「되는 것과 누구
이름으로」에 이름으로 적혀 있다), **그 호출들이 같은 자격증명을 썼는지도 못 봤다.**
그러니 PAT·OAuth 도, **호출마다 다른 자격증명**도 배제된 적이 없다. 종류를 못 박으면
다음 사람이 **앱 연결 설정만 뒤진다** — 그것이 이 절이 만들던 막다른 길이다.</sub>

**그래도 행동으로 서는 것은 그대로다.** 종류가 무엇이든 아래 셋은 잰 값이다.

- **호출자가 `Authorization` 에 넣는 값은 인증에 쓰이지 않는다** — 14자 자리표시자로도
  통했고, 그 값으로 신원을 고를 수도 없었다(아래 「되는 것과 누구 이름으로」).
- **권한은 엔드포인트마다 따로 붙는다** — 저장소 역할 불리언이 전부 `false` 인 채로
  `pull_requests=write` 가 성립했다.
- **무엇이 열려 있는지는 환경마다 다르다** — 같은 MCP 도구가 `fleet` 에서 열리고
  여기서 403 이다(아래 두 환경 대조).

<sub>**재지 않은 엔드포인트가 어느 쪽인지는 모른다.** 그러니 이 절의 숫자를 **저장소에
무엇을 쓸 수 있는가의 가늠으로 쓰지 않는다** — 그것은 바로 아래 「엔드포인트 단위」로
읽는다.</sub>

**쓰기를 시도하기 전에 먼저 본다 — 다만 보는 곳이 저장소 역할이 아니다.**

권한이 **엔드포인트 단위**로 붙으므로, 읽을 것도 엔드포인트 단위다. GitHub 은
**방금 그 호출이 무슨 권한을 요구했는지**를 헤더로 되돌려 준다.

```bash
curl -s -D - -o /dev/null -H "Authorization: Bearer $GITHUB_TOKEN" \
  https://api.github.com/repos/OWNER/REPO/issues/1 \
  | grep -i x-accepted-github-permissions
```

<sub>실측 2026-09-14 — 저장소 조회는 `metadata=read`, 이슈 조회는 `issues=read` 가
왔다. 쓰기 엔드포인트에서는 `issues=write` 처럼 **그 쓰기에 필요한 권한 이름**이
온다.</sub>

**저장소 역할 불리언은 단서지 판정이 아니다.**

```bash
curl -s -H "Authorization: Bearer $GITHUB_TOKEN" \
  https://api.github.com/repos/OWNER/REPO | python3 -c \
  "import json,sys; print(json.load(sys.stdin)['permissions'])"
```

`{"admin": false, ..., "push": false, "pull": false}` 처럼 전부 `false` 인데도 읽기가
되는 것은 **저장소가 공개**여서이지 권한이 있어서가 아니다(응답 헤더
`X-Accepted-Github-Permissions: allows_permissionless_access=true`).

**여기서 「그러니 쓰기도 전부 막혔다」로 건너뛰지 않는다.** 이 불리언이 비추는 것은
`contents` 계열의 **저장소 역할**이고, 앱은 그 역할 없이 `issues=write` ·
`pull_requests=write` 만 가질 수 있다. **전부 `false` 인데 이슈 쓰기는 되는 조합이
성립한다.**

<sub>**추정이 섞인 자리다 — 실측 2026-09-12·2026-09-14.** 이 세션에서는 전부
`false` 였고 쓰기도 실제로 403 이었다. **둘이 같이 나온 것은 봤지만, 하나가 다른
하나의 원인인지는 못 봤다.** 그러니 전부 `false` 는 **의심할 근거**이고 판정이
아니다 — 판정은 아래 「403 이라고 다 권한 부족이 아니다」로 한다.</sub>

**`add_repo` 가 `access: push` 로 성공했다고 답해도 이 값이 바뀌지 않을 수 있다.**
실제로 그렇게 나왔고, 그 세션은 PR 도 이슈 코멘트도 못 올렸다. 붙였다는 응답을
권한의 증거로 읽지 않는다.

<sub>고칠 것이 남았다면 저장소 쪽이 아니라 **계정 쪽**이다 — claude.ai 설정에서
GitHub 연결을 다시 붙이거나, 조직 소유자가 이 저장소를 허용 목록에 넣는다. 세션
안에서 할 수 있는 일이 아니다. **다만 거기로 보내기 전에 다른 경로를 재 본다** —
아래 「한 경로의 거절은 그 경로의 값이다」가 그 자리이고, MCP 가 이 문구로 거부된
날 REST 는 열려 있었다. 재 보고도 길이 없을 때 **저자에게 알리고 멈춘다.**</sub>

### 403 이라고 다 권한 부족이 아니다 — 본문으로 가른다

| 본문·헤더 | 무엇이다 | 무엇을 한다 |
| --- | --- | --- |
| `Resource not accessible by integration` | **그 경로의 권한** | 토큰에 **그 엔드포인트** 권한이 없다. **다른 경로를 재 본 뒤**(아래 「한 경로의 거절은 그 경로의 값이다」) 저자에게 알리고 멈춘다 |
| `You have exceeded a secondary rate limit` · `Retry-After` 헤더 · `x-ratelimit-remaining: 0` | **속도** | 기다리면 된다. 권한 문제가 아니다 |
| 그 밖(조직 정책 · SSO · 저장소 잠금 · 프록시가 낸 문구) | **모른다** | 문구를 **그대로** 저자에게 옮긴다 |

**코드만 보고 「권한이 없다」로 결론내면 기다리면 될 것을 계정 설정으로 보낸다.**
거부를 적을 때는 코드가 아니라 **본문 한 줄**을 같이 적는다. 프록시가 낸 403 은
문구가 GitHub 의 것과 아예 다르므로(아래 GraphQL 절) 본문을 읽으면 바로 갈린다.

**부작용 없이 재는 법(권한이 있을 때): 빈 본문으로 POST 한다.** `422` 면 권한이
있고 본문만 거부된 것, `403` 이면 **위 표로 한 번 더 가른다.**

<sub>**「부작용이 없다」는 전건이 붙는다** — 필수 필드가 있는 엔드포인트에서만
참이다. 필드가 전부 선택인 곳에서는 빈 본문이 **실제로 무언가를 만든다**
(`POST /pulls/N/reviews` 는 대기 중 리뷰를, `POST /forks` 는 포크를 만든다).
재기 전에 그 엔드포인트에 필수 필드가 있는지 먼저 본다.</sub>

**비대칭 하나를 기억한다** — `POST /git/refs` 는 403 인데 **`git push` 는 된다.**
**「git API 가 막혔으니 푸시도 안 되겠다」는 틀린 추론이다.**

<sub>**왜 갈리는지는 못 봤다.** 본 것은 두 결과뿐이다 — git 이 REST 가 아닌 git
프로토콜로 간다는 것까지가 아는 것이고, 거기에 자격증명이 **어떻게 실리는지**는
관측하지 않았다. 쓸 때 필요한 것은 이유가 아니라 **한쪽이 막혀도 다른 쪽을 재 본다**는
것이다.</sub>

| **2026-09-15** | **`X-RateLimit-Limit`** — REST 다섯 호출(`GET /user` · `GET /rate_limit` · `GET /repos/{o}/{r}` · `GET .../pulls/{n}` · `POST /pulls`) | 앞 둘 **15000**, 뒤 셋 **5000** — **저장소 조회가 읽기인데 5000 이다.** 「읽기 15000 / 쓰기 5000」의 반례다. **이 다섯 밖을 이 묶음으로 예측하지 않는다** |
| 2026-09-15 | 저장소 권한 불리언 · 빈 본문 `POST /pulls` · GraphQL · `command -v gh` | **2026-09-14 와 같다** — 전부 `false` · `422` + `pull_requests=write` · 403 · 없음 |

**`POST /pulls` 세 행이 이 표가 표인 이유다.** 「이슈·PR 쓰기 열림」은 2026-09-10
의 측정이고, 2026-09-12 에는 `POST /pulls` 가 403 이었고, 2026-09-14 에는 **경로에
따라 갈렸다.** 줄이 늘 때 위치로 가리키면 그 문장이 낡으므로 **무엇을 잰 행인지로
가리킨다** — 이 문단 자신이 한 번 그렇게 낡아서 고쳤다. **잰 날짜 없이 적었다면 이
문서가 거짓말을 했을 것이다.**

**다만 2026-09-12 가 뒤집은 것은 그 범주 전체가 아니다.** 그날 다시 잰 것은
`POST /issues/N/comments` 와 `POST /pulls` **둘뿐**이고, 같은 칸에 묶여 있던 이슈 편집 ·
라벨 · 마일스톤 쓰기는 **그 뒤로 재지 않았다.** 권한이 엔드포인트 단위로 붙는다고 이
문서가 위에서 적었으므로 **묶어서 적힌 범주는 그 안의 하나가 뒤집혀도 통째로 뒤집히지
않는다** — 재지 않은 쓰기 경로를 미리 포기하지 않는다.

그리고 그 날 **`git push` 는 됐다** — 위의 비대칭이 그대로 다시 나왔다. **GitHub
API 가 통째로 닫혀도 가지는 올라간다.**

### 한 번 재고 일반화하지 않는다 — **경로마다 · 환경마다 · 호출마다** 다르다

2026-09-14 에 `POST /pulls` 가 **MCP 로는 403, REST 로는 됐다.** 같은 세션 · 같은
저장소 · 같은 순간이다. 여기까지만 보고 **「REST 가 열린 길이다」로 굳히면 틀린다** —
그날 그 문장을 쓴 뒤에 두 가지가 더 나왔다.

<sub>**「같은 계정에서 경로만 바꿨다」고는 적지 않는다.** 두 인터페이스에 **같은
자격증명이 실리는지를 못 봤기 때문이다** — 오히려 아래에서 REST 쓰기는 `claude[bot]` 로
나가고 `fleet` 의 MCP 쓰기는 `pdw96` 으로 나간다. 붙잡아 둔 것은 **세션 · 저장소 ·
시각**이고, 나온 것은 **두 인터페이스의 결과가 달랐다**는 관측이다. 원인을 경로로 못
박으면 **앱 설치나 자격증명 권한이 다른 쪽**을 다음 세션이 아예 안 잰다.</sub>

**하나 — 되는 것과 누구 이름으로 되는가는 다른 질문이다.** 잰 REST 쓰기 **4건**은 전부
`claude[bot]` 으로 찍혔다(코멘트 3 · 리액션 1). 그런데 **`GET /user` 는 `pdw96` 으로
돈다** — `{"login":"pdw96","type":"User"}` 가 돌아온다. **사람 이름이 돌아오는 조회를
봤다고 해서 쓰기도 그 이름으로 나가지 않는다.**

<sub>**여기서 「읽기와 쓰기에 다른 신원이 붙는다」로 넓히지 않는다.** 신원을 실제로 본
것은 **계정 수준 조회 하나와 저장소 쓰기 넷**이고, **저장소 조회의 신원은 관측하지
않았다.** 오히려 바로 아래 한도·헤더에서 **잰 저장소 조회 둘은 쓰기 쪽과 같은
모양**이었으니 「조회니까 사람 이름이겠지」는 근거가 없다. 갈리는 축이 읽기·쓰기인지 계정수준·저장소인지
**아직 모른다** — 어느 이름으로 나가는지가 필요하면 **그 경로에서 따로 본다.**</sub>

**다만 그 근거는 작성자 필드이지 rate limit 이 아니다.** 앞 판은 「한도까지 다르다(읽기
15000, 쓰기 5000)」를 나란히 근거로 들었는데, **한도가 갈리는 축은 읽기·쓰기가
아니었다.** **잰 계정 수준 둘**(`GET /user` · `GET /rate_limit`)이 **15000** 이고
`X-OAuth-Scopes` 헤더가 빈 값으로 붙었고, **잰 저장소 범위 셋**(`GET /repos/{o}/{r}` ·
`GET /repos/{o}/{r}/pulls/{n}` · `POST /pulls`)이 **전부 5000** 이고 그 헤더가 아예
없었다 — **저장소는 조회도 쓰기와 같은 값이다.** 그러니 **「읽기 15000 / 쓰기 5000」에는
반례가 있다**: 저장소 조회가 읽기인데 5000 이다.

<sub>실측 2026-09-15 · 이 환경 · `curl` + `$GITHUB_TOKEN` — 위 다섯 엔드포인트의
`X-RateLimit-Limit` · `X-RateLimit-Resource`(다섯 다 `core`) · `X-OAuth-Scopes` 를 한
번에 읽었다. **앞 판은 `GET /user`(15000)와 쓰기(5000) 둘만 보고 축을 읽기·쓰기로
읽었다** — 두 점을 잇는 선이 하나가 아닌데 하나로 본 것이고, 이 문서가 표를 쓰는
이유와 같은 실수다. 작성자 필드로 잰 신원 차이(2026-09-14)는 그대로 선다. 무너진 것은
**한도를 그 근거로 든 것**뿐이고, 둘이 같은 자격증명인지 다른 자격증명인지는 **여전히
못 갈랐다** — 헤더가 갈린다는 것까지가 관측이다.

**그리고 이 다섯으로 「축은 계정수준 ↔ 저장소범위다」라고 굳히지 않는다.** 그 분류가
한도를 정한다는 대조는 하지 않았고, **표본 안에서 그렇게 묶였을 뿐**이다. 잰 것은
계정 수준 둘 · 저장소 범위 셋이고 나머지는 재지 않았다. **무너진 것은 읽기·쓰기 축이고,
대신 선 축은 아직 없다** — 새 축을 적기 전에 재지 않은 쪽을 먼저 잰다. 앞 판의 실수를
점 다섯 개로 되풀이하는 것이 이 자리에서 가장 쉬운 일이다.</sub>

<sub>`$GITHUB_TOKEN`·`$GH_TOKEN` 은 둘이 같은 **14자 자리표시자**(`prox…`)다. 진짜
GitHub 토큰이 될 수 없는 길이인데 **이 환경에서는** 이 값을 `Authorization` 헤더에 실어
보내도 통하고, 동시에 **그 값으로는 신원을 고를 수 없다.** **그러니 진짜 자격증명은 다른
데서 실린다 — 어디서 실리는지는 못 봤다.** 프록시가 헤더를 갈아 끼우는 것인지, 헤더는
그대로 두고 다른 층에서 인증되는 것인지는 **가르지 못했다**(`prox…` 라는 값이 프록시를
가리키는 듯 보이지만 그것은 이름이지 관측이 아니다). 「그래도 통한다」는 **이 환경의 값이다** — `fleet` 에서는 재현되지
않았다(레포 훅 `codex-gate` 가 비-`gh` 클라이언트의 GitHub API 직접 호출을 차단해 실행
자체가 안 된다). **저장소가 훅으로 막으면 프록시가 무엇을 하든 그 앞에서 끝난다.**</sub>

**둘 — MCP 쓰기는 사람 이름으로 나가는데, 열리고 닫히는 것이 환경별이다.**
`add_issue_comment` 로 단 코멘트는 작성자가 **`pdw96`**(`performed_via_github_app:
Claude`)이다 — 저자가 `Fleet` 환경에서 쟀다. 그런데 **같은 도구가 이 저장소의 환경
(`early warning based on ERP`)에서는 403** 이다(코멘트 · 리액션 · `create_pull_request`
셋 다). 그러니 **「MCP 는 막혔다」도 「MCP 가 답이다」도 둘 다 틀렸다** — 환경을 묻지
않은 문장이기 때문이다.

그날 실제로 한 일의 순서가 이 절이 있는 이유다. MCP 가 403 을 내자 위 표의
**2026-09-12 행을 보고 「확인됐다」며 멈췄다** — 저자에게 「PR 은 직접 여셔야
한다」고 알리기까지 했다. 그 행은 **MCP 로 잰 값**인데 그것을 **엔드포인트 전체의
성질**로 읽은 것이다. 아래 「부작용 없이 재는 법」을 한 번 돌렸으면 5초에 갈렸다.

```bash
curl -sS -i -X POST \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github+json" \
  -H "Content-Type: application/json" \
  -d '{}' https://api.github.com/repos/OWNER/REPO/pulls
```

`422 "base", "head" weren't supplied` 와 `X-Accepted-Github-Permissions:
pull_requests=write` 가 왔다 — **권한이 있고 본문만 거부된 것.** 본문을 버리면
(`-o /dev/null`) 이 문장의 근거가 화면에 안 남고, 403 일 때 위 표로 가를 것도
없어진다. 그래서 `-i` 로 **헤더와 본문을 같이** 본다.

<sub>실측 2026-09-14 · **2026-09-15 에 위 명령 그대로 다시 재도 같았다**(422 ·
같은 헤더).</sub>

<sub>`Content-Type: application/json` 을 빠뜨리면 프록시가 먼저 가로채 *“Request
bodies must declare Content-Type”* 를 낸다. GitHub 의 답이 아니므로 그것을 403
판정에 넣지 않는다.</sub>

**그러니 한 경로의 거절은 그 경로의 값이다.** 이미 `POST /git/refs` 는 403 인데
`git push` 는 되는 비대칭을 이 문서가 들고 있었다 — 같은 모양이 MCP 와 REST
사이에도 있다. **하나가 막히면 나머지를 재 보고 나서 저자에게 알린다.**

**다만 이 「나머지를 재 본다」는 GitHub 이나 프록시가 돌려준 HTTP 권한 거부에만
건다.** 위 「세 관문」의 **분류기 거부에는 걸지 않는다** — 거기서는 그 자리에서
멈춘다. 둘을 같은 모양으로 읽으면 분류기가 막은 것을 다른 도구로 도는 것이
「경로를 재 보는 일」처럼 보이는데, 그것이 바로 우회다.

#### 쓰기 신원이 틀리면 리뷰 봇이 안 붙는다 — 그리고 **신호가 올 때도 안 올 때도 있다**

**되는 것부터 적는다.** 사람 이름(MCP)으로 건 `@codex review` 는 **3~4분 안에 리뷰가
온다** — 저자가 `fleet` 에서 5회 걸어 5회 다 동작했다. 그러니 이 절은 「봇은 리뷰를
못 부른다」가 아니라 **「어느 이름으로 부르느냐가 가른다」**이다.

| 무엇 | 봇 이름으로 하면 | 실패가 보이나 | 어디서 · 언제 |
| --- | --- | --- | --- |
| `@codex review` 트리거 (REST 명의) | 코덱스가 **연결되지 않은 계정**이라며 거부 — 「create a Codex account and connect to github」 | **보인다** — 거부 메시지가 온다 | **미기록** — 아래 「출처」가 봇 연동은 `fleet` 이라고만 적는다 |
| 봇이 연 PR (자동 리뷰 경로) | CodeRabbit 이 **`Review skipped / Bot user detected`** | **보인다** — 푸시마다 갱신되는 skip 코멘트 | 이 환경 · `#70`~`#72` · 2026-09-14 |
| `@coderabbitai review` 코멘트 (REST 명의) | 아무 반응이 없다 | **안 보인다** — 31분 무응답, 거절 메시지조차 없음 | 이 환경 · 2026-09-14 |
| `ccr/ready_for_review` 로 초안 해제 | 행위자가 `claude[bot]` 으로 기록됐고 **자동 리뷰가 오지 않았다** — 다만 그 PR 은 **작성자도 `claude[bot]`** 이라 둘 중 무엇이 막았는지는 못 가른다 | **안 보인다** | 이 환경 · `#70`~`#72` · 2026-09-14 |

**그러니 「무응답 = 거부당했다」로 읽지 않는다.** 같은 CodeRabbit 이 자동 리뷰 경로에는
명시적 skip 코멘트를 남기고 코멘트 트리거 경로에는 아무것도 안 남겼다 — **신호의 유무가
봇이 아니라 경로에 딸려 있다.** 무응답은 「아직 판정이 없다」이지 판정이 아니다.

`#70`·`#71`·`#72` 에서 넷 중 셋을 차례로 밟았다. 초안으로 열어 건너뛰었고, ready 로
풀었더니 다시 건너뛰었고, 트리거 코멘트는 무응답이었다. **쓰기가 성공한 것과 그 쓰기가
뜻을 갖는 것은 다르다.**

**봇이 연 PR 을 봇이 ready 로 풀었더니 리뷰가 오지 않았다.** 그때 리뷰를 부른 것은
**ready 직후 함께 건 MCP 수동 트리거**다. 이것은 **그 조건에서 통한 우회로**이지 ready
일반의 성질이 아니다 — 위 표가 적었듯 작성자와 행위자가 함께 봇이어서 둘을 못
가른다. `authority-line` 25행은 ready 전환 자체를 **리뷰를 부르는 행위**로 정의하므로,
사람이 연 PR 에서는 ready 만으로 발화할 수 있고 거기에 트리거를 덧붙이면 **리뷰가 두
번 돈다.** 대조 실험이 생기기 전에는 여기까지가 아는 것이다.

**그리고 어느 쪽이든 누르는 것은 저자다.** `authority-line` 은 리뷰 요청과 draft↔ready
전환을 한 칸에 묶어 사람에게 남긴다. **여기 적힌 것은 저자가 시켰을 때 무엇을 눌러야
하는가이지, 눌러도 된다는 뜻이 아니다.**

그래서 **쓰기 경로는 되는 것이 아니라 이름으로 고른다** — 코멘트와 PR 생성은
**여기서 재 본 경로 중에서는** MCP GitHub 도구만 사람 이름으로 나갔다. 조회는 REST 로
한다.

**「유일한 길」이라고 적지 않는 이유는 이 문서가 그 실수를 이미 두 번 했기
때문이다.** 잰 것은 REST 와 MCP 둘뿐이고, 다른 자격증명이나 다른 클라이언트를
배제한 측정이 아니다. 그러므로 **MCP 가 403 이어도 「세션 안에서 고칠 수 없다」고
먼저 결론내지 않는다** — 그 환경에서 사람 이름으로 나가는 다른 경로가 있는지를
재 보고, 없을 때 저자에게 알린다. 그때 저자가 할 일은 claude.ai Settings →
Connectors 에서 GitHub 을 다시 붙이거나 그 저장소에 앱 접근을 주는 것이다.

그리고 그때 저장소 권한 불리언은 **전부 `false` 였다.** 위 「전부 `false` 는
의심할 근거이고 판정이 아니다」가 이날 실측으로 한 번 더 섰다 — 전부 `false` 인
채로 PR 이 두 개 열렸다.

<sub>**다만 한 자격증명 안에서 둘이 공존한다는 확인은 아니다.** 불리언은 **조회
응답**에서 왔고 PR 생성은 **`claude[bot]` 명의의 다른 쓰기 요청**이다. 둘에 같은
자격증명이 실렸는지는 못 봤다(위 「되는 것과 누구 이름으로」). 그러니 여기서 서는 것은
**「전부 `false` 를 보고 쓰기를 포기하지 마라」는 행동 규칙**뿐이고, 「쓰기 자격증명의
권한 단서를 무시해도 된다」는 아니다 — 그 단서는 **쓰기 엔드포인트의
`X-Accepted-Github-Permissions`** 로 따로 본다.</sub>

<sub>**`fleet` 쪽 날짜가 행마다 없는 것도 미기록이다.** 저자의 측정이 `2026-09-14~15`
범위로만 넘어왔고 **어느 항목이 어느 날인지 갈려 있지 않다.** 범위를 행마다 베껴
적으면 다섯 행이 다 같은 날 잰 것처럼 보이므로 그렇게 하지 않는다 — 이 표의 `fleet`
칸이 낡았는지 보려면 **그 환경에서 항목별로 다시 잰다.**</sub>

**같은 MCP 도구가 한쪽에서 열리고 한쪽에서 닫힌다.** 그러므로
`403 Resource not accessible by integration` 은 **경로만으로도 환경만으로도 정해지지
않는다 — 둘의 조합이다.** 이 환경에서 REST 는 열리고 MCP 는 닫혔으니 경로가 답을
바꾸고, 같은 MCP 가 `fleet` 에서 열리니 환경도 답을 바꾼다. **한 축으로 접으면 다음
세션이 나머지 축을 안 잰다** — 이 절이 막으려는 것이 그것이다.

**그리고 표에 못 잰 칸이 하나 있다.** 이 환경의 MCP 작성자 이름은 쓰기가 403 이라
관측되지 않았다 — 그러니 「신원이 붙는 방식까지 두 환경이 같다」고는 아직 말할 수
없다. **값이 같게 나온 것**은 읽기 신원 · REST 쓰기 작성자 · GraphQL 세 줄인데, 그 셋은
**양쪽이 서로 다른 것으로 쟀거나 한쪽이 미기록이다**(위 각주). 그러니 이 표가 말하는
것은 「같은 경로로 같았다」가 아니라 **「다른 경로로도 같은 값이 나왔다」**까지다.

**그래서 이 문서의 값을 다른 저장소 문서로 옮기지 않는다.** 저자가 이 정리를 `fleet` 의
`AGENTS.md` 에 그대로 옮겨 커밋했다가 되돌렸다 — **`fleet` 에서는 MCP 쓰기가 멀쩡히
도는데 이 환경의 403 을 규율로 써버린 것**이다. 측정은 **어느 환경에서 쟀는지와 함께**
적고, 옮길 때는 그 환경에서 다시 잰다.

<sub>출처 — 쓰기 신원과 봇 연동 동작은 저자가 `pdw96/fleet` 세션에서 쟀다(2026-09-14~15,
`fleet` PR `#339` 가 `AGENTS.md` 「Codex 봇 운영」 절에 반영). 이 환경의 403 과 코멘트
트리거 무응답은 여기서 쟀다.</sub>

## GraphQL 은 클라우드에서 안 된다 — 다만 계정이 막힌 것이 아니다

403 이고, **막는 것은 GitHub 이 아니다.** 돌아오는 본문이 *“not available from Claude
Code sessions”* 라고 스스로 밝히고 Anthropic 문서를 가리킨다 — GitHub 의 문구가
아니다. 연산 종류에서 인증 이전에 막으므로 **토큰을 바꿔도 소용없다**: 가짜 토큰을
붙여도 문구가 한 글자도 안 바뀌었다. (REST 는 반대로 가짜 토큰에도 `200` 이 왔다 —
**호출자가 넣은 문자열이 인증에 쓰이지 않는다**는 뜻이다. 헤더가 갈아 끼워지는 것인지
헤더와 무관하게 인증되는 것인지는 **가르지 못했다**.)

**막힌 것은 이 환경이지 계정이 아니다.** 저자의 로컬은 200 이다. 그래서 규칙은
**「클라우드 세션에서 Projects·Discussions·보안 경보를 하자고 제안하지 않는다」**
이지 「그 기능을 설계에서 지운다」가 아니다.

### 거절 문구가 우회로를 알려 준다 — 그리고 그 문구는 바뀐다

2026-09-14 에 다시 재니 **문구가 통째로 달라져 있었다.** 예전에는 *“only the
pinned set of PR-review operations is served.”* 였는데, 지금은 **REST 대체 경로를
이름까지 적어 준다.**

| CCR 경로 (`api.github.com`) | 무엇 |
| --- | --- |
| `GET  /repos/{o}/{r}/pulls/{n}/ccr/review_threads` | 스레드 목록 — `resolved` · `outdated` 가 붙어 온다 |
| `POST /repos/{o}/{r}/pulls/{n}/ccr/comments/{id}/resolve` (·`/unresolve`) | 스레드 해소 |
| `PUT`·`DELETE /repos/{o}/{r}/pulls/{n}/ccr/auto_merge` | auto-merge |
| `POST /repos/{o}/{r}/pulls/{n}/ccr/ready_for_review` · `/convert_to_draft` | draft ↔ ready |

**이 문서는 「스레드 해소는 GraphQL 이라 기술적으로도 안 된다」고 적고 있었다. 지금
그것은 거짓이다.** 날짜를 붙이라는 규칙이 잡으라고 있는 것이 정확히 이 자리다.

> **그래도 해소·auto-merge·ready 는 여전히 사람이 한다.** 길이 열린 것이 규율을
> 지우지 않는다 — `authority-line` 의 **「막혀 있어서 안 하는 것이 아니라 하지
> 않기로 해서 안 한다」**가 그대로 적용된다. **`ccr/resolve` 와 `ccr/auto_merge`
> 는 `enable_pr_auto_merge` 와 같은 칸에 두고 이름째로 부르지 않는다.**

읽기(`GET .../ccr/review_threads`)는 다르다 — 부작용이 없고, **무엇이 아직
해소되지 않았는지를 저자에게 알리는 데 쓴다.**

**`gh` CLI 의 하위명령 중에 GraphQL 클라이언트라 여기서 실패하는 것이 있다** —
`gh pr view --json number` 가 그렇다. `gh api repos/{o}/{r}/…`(REST)는 돈다.
「`gh` 가 안 된다」가 아니라 **그 하위명령이 GraphQL 인가**로 갈린다.

**잰 것은 양쪽으로 하나씩이다.** 그러니 이것은 **가르는 기준**이지 어느 쪽이 얼마나
되는지의 셈이 아니다 — 「상당수가 GraphQL 이다」도 「REST 는 `gh api` 뿐이다」도 여기
있는 관측으로는 말할 수 없다. **쓸 하위명령이 생기면 그것을 따로 잰다.**

**`--json` 에는 필드를 반드시 붙인다.** 필드 없이 쓰면 `gh` 가 요청을 보내기 전에
필드를 요구하며 끝나므로, 그 실패는 전송 방식에 대해 **아무것도 말해 주지 않는다** —
403 을 봤다고 착각하기 딱 좋은 자리다.

**예시는 읽기 쪽으로만 든다.** `gh pr comment` 처럼 **쓰는** 하위명령은 전송 방식을
확인하자고 돌리는 순간 실제로 코멘트가 달리고 리뷰 봇까지 깨운다. 머지 하위명령은
거기 더해 위 「이름째로 부르지 않는다」와 같은 칸이다. 전송 방식을 설명하자고 실행
명령을 적어 두면 다음 세션이 그것을 대체 경로로 집는다.

<sub>**이 줄에는 잰 자리가 붙어 있지 않다 — 그래서 지금은 미검증으로 둔다.** 어느
하위명령이 GraphQL 인지는 `gh` 의 구현이고 판을 따라 바뀌는데, 어느 판에서 언제
쟀는지가 없으면 바뀐 뒤에도 계속 실패한다고 오판한다. **2026-09-15 에 이 환경에서
재니 `gh` 는 설치조차 되어 있지 않았다**(`command -v gh` 가 비었다 — 아래 「새 세션은
맨바닥에서 시작한다」와 같은 관측이다). 그러니 이 문장은 `gh` 가 있는 다른 자리에서
온 값이다. 다시 쓸 일이 생기면 그 환경에서 `gh --version` 과 `GH_DEBUG=api` 로 다시
재고, **판과 날짜를 함께** 적는다.</sub>

<sub>실측 2026-09-14 · PR `#65` — GraphQL `POST /graphql` 403, `GET
.../pulls/65/ccr/review_threads` 200(미해소 6건). **2026-09-15 에 이 환경에서 다시 재도
같았다** — 부작용 없는 읽기 질의(`viewer { login }`)로 건 `POST /graphql` 이 403 이고,
거절 문구가 **위 표의 경로 넷을 그대로 나열했다**(문구가 또 바뀌지는 않았다).
`GET .../pulls/72/ccr/review_threads` 는 200(14건 전부 미해소).</sub>

<sub>**`POST .../ccr/ready_for_review` 는 그 뒤 실제로 불렸다** — 2026-09-14,
`#70`·`#71`·`#72` 에 각각 `200 {"draft":false}`. **저자가 직접 지시해서 누른
것이고 위 규율은 그대로다** — 「사람이 한다」가 「기술적으로 막혀 있다」였던 적이
없다는 것이 이것으로 다시 확인됐을 뿐이다. 그리고 **눌러도 리뷰 봇은 붙지
않았다**(행위자가 `claude[bot]`) — 위 「쓰기 신원이 틀리면」을 본다. 나머지 쓰기 쪽
CCR 경로(`resolve`·`auto_merge`·`convert_to_draft`)는 여전히 **부르지 않았으므로
미검증**이다.</sub>

## 새 세션은 맨바닥에서 시작한다

작업 디렉터리가 **비어 있고**, `gh` CLI 가 **없다.** 첫 수는
`add_repo` → `git clone` → `register_repo_root` 이고, **그 셋을 하기 전에는
`CLAUDE.md` 조차 실리지 않는다.** 그 셋은 저장소 파일로 없앨 수 없다 — 훅을
읽으려면 clone 이 먼저여야 하는 고리가 생긴다. 저장소가 맡을 수 있는 것은
**clone 뒤의 준비**다.

**커넥터도 세션 생성 시점에 붙는다.** 저자가 MCP 를 켜도 **이미 떠 있는 세션에는
안 붙는다.** 「켰는데 왜 없지」의 답은 「세션을 새로 열어라」다.

<sub>실측 2026-09-09 ~ 2026-09-12 · 관제탑과 레인 세션들. **다시 재지 않았다** —
세션을 새로 여는 것이라 이 세션 안에서 확인할 수 없다.</sub>

## 아티팩트는 읽기가 비싸고, 변경 알림이 없다

- **`curl` 로는 못 읽는다** — `200` 이 오지만 앱 껍데기다. 내용이 사는
  `*.frame.claudeusercontent.com` 은 404. **그래서 CI 는 아티팩트를 원리적으로
  검사할 수 없다.**
- **재발행 알림이라는 기능이 없다** — 켜는 토글을 찾지 마라. 게이트웨이가 404 로
  거절한다(여섯 번 재현). **지도의 변경은 발행 전에 직접 읽는 것이 정상 경로다.**
- **읽는 것 자체가 비싸다** — 70KB 대를 넘기면 `action: "read"` 한 번이 세션
  컨텍스트의 2~3% 를 먹는다. **발행할 것이 있을 때만 읽고, 고칠 것이 둘 이상이면
  묶어서 한 번에 올린다.**
- **이 세션 밖에서도 바뀐다.** 더 새 판 위에 얹지 않은 발행은 **거절된다** —
  사고가 아니라 방어가 작동한 것이다. 거절당하면 **돌려받은 판 위에 병합한다.**
  준비한 내용을 그대로 다시 보내면 남의 판이 지워진다.

<sub>실측 2026-09-09 ~ 2026-09-12 — 404 는 여섯 번 재현했고, 읽기 비용은 세션
컨텍스트로 쟀다.</sub>
