## 1. 왜 이것을 먼저 하는가

**사용자 결정(2026-09-03).** 남은 계획 5개 중 완제품 로트·완제품창고를 첫 번째로
진행한다. 선택 근거로 제시하고 사용자가 고른 내용:

- 완제품 재고가 없으면 **후속 ③ 출하 리스크가 성립하지 않는다** — 출하일에 완제품이
  충분한지 잴 대상 자체가 없다.
- `/sales`(영업관리)가 **빈 껍데기로 남아 있는 유일한 메뉴**다(실측:
  `frontend/app/sales/page.tsx`는 "준비 중" 안내문만 렌더한다).
- 후속 ① 재고이동은 두 창고 합산 가용 가정 때문에 **총 가용량을 바꾸지 않아** 리스크
  판정에 미치는 영향이 가장 작다 → 뒤로 미뤄도 손해가 없다.

확정된 우선순위(1번만 사용자 확정, 2~4번은 **추정 — 사용자가 "OK"로 확인**):

## 3. 범위

### 포함 (사용자 확정)

1. **`FinishedGoodsLot` 엔티티** + `완제품창고` 도입, 창고 상수 자재용/완제품용 분리
2. **`QualityInspection` 엔티티 + 품질관리 모듈(`/quality`)** — IQC·PQC·OQC 세 유형의
   검사 기록을 조회. ERP 메뉴에 품질관리 추가
3. **OQC 이동 규칙** — 완제품창고에 있으려면 OQC 합격이어야 한다. DB 제약으로 건다
4. **유효기간 설정기간을 기준정보로 이관** — 제품·자재에 `shelf_life_days`를 두고
   로트 유효기간을 거기서 파생. 기준정보관리 화면에 노출
5. **자재 시드 재작성** — 유효기간을 설정기간 파생으로 바꾸고, 만료 부족 시나리오를
   같은 효과로 재구성. **무기한 품목을 일부 섞는다**
6. **시드**가 합성 완제품 로트와 검사 기록을 생성 (생산 실적에서 파생, 영구 보존)
7. **조회 API** — `GET /api/finished-goods`, `GET /api/quality-inspections`
8. **`/sales` 화면** — "준비 중" 안내문을 실제 완제품 재고 화면으로 교체
9. **문서·CI** — README 갱신, `sales.png`·`quality.png` 스크린샷 추가,
   `test_readme.py` 갱신
10. **테스트** — pytest(모델 제약·시드·서비스·API) + 프론트 컴포넌트 테스트

### 명시적 제외

- **쓰기 워크플로 전부**(사용자 확정: "조회만 — 데이터는 시드가 생성"). 화면에서 로트
  생성·재고이동·검사 판정 입력·수량 수정을 하지 않는다. POST/PATCH API를 추가하지 않는다.
- **검사 기준·검사 항목·측정값.** `QualityInspection`은 유형·대상·검사일·판정(합격/불합격)
  ·사유만 갖는다. 규격 상하한과 측정치 관리는 후속이다.
- **검사 결과가 자재·생산 판정에 미치는 영향.** 결정 G-2 참조 — 이번엔 OQC만 수량
  흐름(완제품창고 이동 가부)에 관여한다.
- **출하·`Shipment` 엔티티, 세 번째 리스크 타입.** `risk_type: Literal["납기","자재"]`를
  **건드리지 않는다**(`contracts.py:142`). 완제품 부족 판정도 하지 않는다.
- **자재 재고이동**(후속 ①), **ERP 서브메뉴**(후속 ④), **설비**, **AI 브리핑**
- **완제품 FIFO 소진 시뮬레이션.** 출고(출하)가 없으므로 차감할 수요가 없다.
  14일 전망은 자재에만 남는다.
- **수주·거래처 엔티티.**

## 4. 설계 결정과 근거

### 결정 A — 창고 상수를 자재용/완제품용으로 분리한다

`WAREHOUSES`에 `완제품창고`를 그냥 추가하면 **자재 로트의 CHECK 제약이 자동으로
넓어져 자재를 완제품창고에 넣을 수 있게 된다**(실측: `models.py:19-21`이
`WAREHOUSES`를 그대로 SQL로 굽는다). 그래서:

```python
RAW_MATERIAL_WAREHOUSE = "원재료창고"
PRODUCTION_WAREHOUSE = "생산창고"
FINISHED_GOODS_WAREHOUSE = "완제품창고"

MATERIAL_WAREHOUSES = (RAW_MATERIAL_WAREHOUSE, PRODUCTION_WAREHOUSE)
FINISHED_GOODS_WAREHOUSES = (PRODUCTION_WAREHOUSE, FINISHED_GOODS_WAREHOUSE)
```

**생산창고는 두 집합에 모두 들어간다.** 라인 옆에는 투입 대기 자재와 갓 생산된
완제품이 같이 있고, 사용자가 말한 "생산창고에서 생산된 완제품을 완제품창고로 이동"이
그 상태를 전제한다. 기존 `WAREHOUSES` → `MATERIAL_WAREHOUSES`로 이름을 바꾼다
(참조 5개 파일, 실측). `FinishedGoodsLot`도 자기 목록에서 CHECK 제약을 굽는다.

**기각안:** 창고를 별도 테이블로 승격 — 창고가 3개뿐이고 속성이 이름밖에 없어 조인만
늘고 얻는 게 없다. 후속 ①에서 이동 이력이 생기면 그때 재검토한다.

### 결정 B — 완제품 로트는 생산 실적에서 **파생**되며, 실적이 진실이다

선행 문서가 남긴 핵심 질문("`actual_quantity`와 로트 수량이 어긋날 때 무엇이
진실인가")에 대한 답이다. 이번 범위가 조회 전용이므로 **시드가 실적을 읽어 로트를
만든다.** 화면에서 따로 입력하지 않으므로 어긋날 경로가 없다.

회귀 테스트로 못 박는다: `완제품 로트 수량 합계 == 과거 actual_quantity 합계`.
**PQC 불합격이 있어도 이 등식은 유지된다** (결정 G-2).

### 결정 C — 로트는 **영구 기록**이다. 지우지 않는다

> **사용자 정정(2026-09-03):** *"원재료든 제품이든 LOT는 영구히 관리돼야 한다.
> 출하되면 완제품창고에 있는 완제품의 LOT 재고에 한해서 출하돼야 한다."*
>
> 초안의 "최근 14일 생산분만 로트로 만들고 그 이전은 출하된 것으로 간주" 안은
> **폐기한다.** 로트를 임의로 안 만드는 것은 "영구히 관리"와 정면으로 어긋난다.

- 시드는 **과거 생산 실적 전 기간**(현재 30일 이상)에 대해 완제품 로트를 만든다.
- 로트 행은 어떤 이유로도 삭제하지 않는다. 만료돼도 `만료` 상태로 목록에 남는다.
  (자재 로트가 이미 같은 방식이다 — 실측: README 「데이터 모델」의 로트 목록 설명)
- **결과: 출하가 아직 없으므로 완제품 재고는 차감되지 않고 누적된다.** 이는 후속 ③
  출하 리스크가 붙어야 해소되며, 그때 차감은 **완제품창고의 OQC 합격 로트에서만**
  일어난다. 이 한계를 README와 `/sales` 화면 안내문에 명시한다.

### 결정 C-2 — 생산창고 → (OQC 합격) → 완제품창고

> **사용자 발화(2026-09-03):** *"생산창고에 생산실적으로 만들어진 제품은 OQC를
> 통해서 통과한 품목에 한하여 완제품창고로 재고이동한다."*

`FinishedGoodsLot.qc_status: Literal["검사 대기", "합격", "불합격"]`을 두고,
불변식을 **DB CHECK 제약**으로 건다:

```sql
warehouse <> '완제품창고' OR qc_status = '합격'
```

시드는 네 상태를 모두 만든다 — 최근 1일 이내 생산분은 `검사 대기`(생산창고), 그 다음
날 생산분은 `합격`이지만 아직 `생산창고`(**이관 대기**), 그 이전은 `합격`(완제품창고),
그리고 고정 주기로 뽑은 소수가 `불합격`(생산창고)이다.

**반대 방향은 강제하지 않는다.** `합격 ⟺ 완제품창고`로 못 박으면 "합격했지만 아직 안
옮긴" 상태를 표현할 수 없고, 후속 ①(재고이동)이 다룰 대상이 사라진다. 이관 대기 로트를
시드가 실제로 만들기 때문에 이 한쪽 방향 제약이 화면에서 검증된다.

**불합격 로트 처리(사용자 확인 완료):** 생산창고에 남기고 **출하 가능 재고에서
제외**하되 목록에는 남긴다(결정 C의 영구 보존). 폐기·재작업 처리는 후속이다.

### 결정 D — 완제품 로트 부여 단위는 (제품, 생산일)

하루 생산분을 한 로트로 묶고, 로트번호는 `LOT-{제품코드}-{YYMMDD}`로 결정적으로
만든다(고정 시드 재현성 유지. 자재 로트의 `LOT-{자재코드}-{순번}`과 같은 형태다). 여러 오더가 같은 제품을 같은 날 생산하면 한 로트로
합친다 — 소재 제조에서 같은 날 같은 라인 산출을 한 로트로 보는 게 자연스럽고,
오더별로 쪼개면 로트 수가 불필요하게 불어난다. 유일키는 자재 로트와 같은 모양으로
`(product_id, lot_number, warehouse)`를 쓴다(후속 ①의 부분 이동 대비).
**추정 — 사용자 확인 완료.**

### 결정 E — 유효기간은 **기준정보의 설정기간**에서 파생한다

> **사용자 정정(2026-09-03):** *"유효기간은 원재료와 완제품 둘 다 적용돼야 한다.
> 각 유효기간은 사내 내부 프로세스에 따른 설정기간으로 지정해야 한다. 이에 대한
> 정보는 기준정보 모듈 내에서 관리돼야 한다."*

- `Product.shelf_life_days: int | None`, `Material.shelf_life_days: int | None` 추가
- 완제품 로트 `expiry_date = produced_date + shelf_life_days`
- 자재 로트 `expiry_date = received_date + shelf_life_days`
- 예정 입고 `expiry_date = scheduled_date + shelf_life_days`
- `shelf_life_days`가 `None`이면 유효기간 없음(무기한)

**로트의 `expiry_date`는 계산해서 저장하고, 저장된 값이 진실이다.** 읽을 때마다
다시 계산하지 않는다. 로트 라벨에 찍혀 나가는 값이라 나중에 사내 설정기간을 바꿔도
이미 부여된 로트의 만료일은 안 바뀌는 것이 현실이고, 기존 판정 코드
(`material_risk.py`)가 `expiry_date`를 그대로 읽고 있어 변경 범위도 좁다.

**무기한 품목을 허용한다(사용자 선택).** 그래야 README·FEFO의 "유효기간 없는 로트는
폐기되지 않으므로 가장 마지막에 쓴다" 규칙과 그 테스트가 죽은 코드가 되지 않는다.
시드는 자재·제품 각각에 무기한 품목을 최소 하나씩 섞는다.

**기준정보 화면 노출:** `MasterItemResponse`에 `shelf_life_days`를 추가한다. 또한
제품도 이제 로트를 가지므로 `lot_count`가 제품 행에서도 값을 갖는다 —
`contracts.py:105`의 "제품에는 안전재고·로트 개념이 없다" 주석을 고쳐야 한다
(안전재고는 여전히 자재만).

### 결정 G — 검사 기록은 `QualityInspection` 한 테이블, 대상은 유형별 FK

> **사용자 발화(2026-09-03):** *"IQC, PQC, OQC의 기록은 품질관리 모듈을 만들어서
> 관리"* → 세 유형 전부 이번 범위 (사용자 선택).

```python
class QualityInspection:
    id
    inspection_type: Literal["IQC", "PQC", "OQC"]
    inspected_date: date
    result: Literal["합격", "불합격"]
    reason: str | None            # 불합격 사유. 합격이면 None
    material_lot_id: int | None       # IQC 대상
    daily_production_id: int | None   # PQC 대상
    finished_goods_lot_id: int | None # OQC 대상
```

유형별로 대상 테이블이 다르므로 **nullable FK 3개 + CHECK 제약**으로 "유형에 맞는
대상 하나만 채워져 있음"을 DB에서 강제한다:

```sql
(inspection_type='IQC' AND material_lot_id IS NOT NULL
   AND daily_production_id IS NULL AND finished_goods_lot_id IS NULL)
OR (inspection_type='PQC' AND daily_production_id IS NOT NULL
   AND material_lot_id IS NULL AND finished_goods_lot_id IS NULL)
OR (inspection_type='OQC' AND finished_goods_lot_id IS NOT NULL
   AND material_lot_id IS NULL AND daily_production_id IS NULL)
```

**기각안 1 — `target_type` + `target_id` 범용 컬럼:** FK 무결성이 사라져 존재하지
않는 대상을 가리키는 기록을 DB가 막지 못한다. 대상이 3종뿐이라 얻는 유연성도 없다.
**기각안 2 — 유형별 테이블 3개:** 목록·화면이 세 곳으로 갈라져 "품질관리 모듈에서
기록을 관리한다"는 요구와 어긋나고, 공통 컬럼이 세 번 반복된다.

**검사 대기 = 기록이 없는 상태.** `result`에 `검사 대기`를 넣지 않는다. 검사를 안 한
것은 판정이 아니다. `FinishedGoodsLot.qc_status`는 **OQC 기록에서 파생된 캐시**이며
`QualityInspection`이 진실이다 — 기록 없으면 `검사 대기`, 있으면 그 판정.
쓰기 경로가 시드 하나뿐이라(실측: `routes.py` 쓰기 1개) 캐시가 어긋날 경로가 없고,
**둘의 일치를 회귀 테스트로 못 박는다.** 후속 ①에서 쓰기가 생기면 그때 갱신 책임을
정한다. 캐시를 두는 이유는 결정 C-2의 창고 불변식을 **DB CHECK로 걸기 위해서**다
(테이블 간 참조는 SQLite CHECK로 표현할 수 없다).

### 결정 G-2 — 이번 범위에서 수량 흐름에 관여하는 검사는 **OQC뿐**

- **IQC(수입검사)** — 시드는 모든 자재 로트에 **합격** 기록을 만든다. 창고에 들어와
  있는 자재는 검사를 통과했다는 뜻이기 때문이다. 단위는 **물리적 로트**(자재, 로트번호)
  이지 로트 행이 아니다 — 한 로트가 두 창고에 나뉘어 있어도 입고 시점에 한 번 검사한
  것이므로 기록을 두 번 남기지 않는다(기준정보가 보유 로트를 로트번호로 세는 것과 같은
  규칙). 처음엔 행마다 남겨 RM-03의 로트가 IQC 두 건으로 잡혔고, PR #9 리뷰에서
  지적받아 고쳤다. 불합격 자재의 반품·격리는 자재 가용
  재고와 14일 판정을 바꾸는 일이라 **후속**으로 뺀다. 이번에 손대면
  `material_risk.py`와 기존 회귀 테스트를 대량으로 흔든다.
- **PQC(공정검사)** — 생산 실적일 일부에 **불합격** 기록을 만든다. 단 **수량에는
  영향을 주지 않는다.** 영향을 주면 결정 B의 등식(`로트 합계 == 실적 합계`)이 깨지고
  납기 판정의 최근 7일 평균까지 흔들린다. 이번엔 "그날 공정 이상이 있었다"는 기록이다.
- **OQC(출하검사)** — 완제품 로트의 창고 이동 가부를 정한다(결정 C-2).

이 선은 **기존 납기·자재 판정을 하나도 건드리지 않기 위한 것**이다. 검사 결과를
재고·능력 판정에 반영하는 것은 그 자체로 한 번의 작업이며 후속으로 남긴다.

> **사용자 확인(2026-09-03):** *"현재 있는 재고들에 한해서 오케이."* — IQC 전건
> 합격은 **이미 창고에 있는 로트에 한한** 규칙이라는 뜻으로 확정한다. 불합격분은
> 애초에 재고로 들어오지 않았으므로 이 데모의 로트 집합에 없다.

### 결정 F — 조회 API 두 개

`GET /api/finished-goods` — 제품별 재고 요약 + 로트 목록을 한 응답에. `/materials`가
자재별 재고 + 로트 목록을 한 응답으로 주는 것과 같은 모양이라(실측: `MaterialResponse`가
`lots` 포함) 프론트 패턴을 그대로 재사용할 수 있다.

제품별 요약은 **서로 겹치지 않고 합이 로트 행 합계와 같은 다섯 칸**이다. 겹치면 같은
재고가 두 칸에 잡혀 출하 가능 수량이 실제보다 많아 보인다. 로트의 화면 상태도 이 다섯과
1:1로 대응시킨다.

| 요약 항목 = 로트 상태 | 정의 |
|---|---|
| 출하 가능 | 완제품창고 + 미만료 (제약상 OQC 합격) |
| 이관 대기 | OQC 합격이지만 아직 생산창고 + 미만료 |
| 검사 대기 | 아직 OQC 기록이 없음 + 미만료 |
| 불합격 | OQC 불합격 + 미만료 |
| 만료 | 유효기간이 지남 (창고·검사 무관) |

만료를 가장 먼저 보는 이유는 만료 로트가 완제품창고에 남아 있어도 출하할 수 없기
때문이다. 만료 판정에 `유효기간 <= 기준일`을 쓰는 것은 자재의 가용 조건
(`입고일 <= 날짜 < 유효기간`)과 같은 규칙이다.

`GET /api/quality-inspections` — 검사 기록을 검사일 내림차순으로. 각 행은 유형, 검사일,
대상 표기(IQC: 자재코드·로트번호 / PQC: 제품코드·오더번호 / OQC: 제품코드·로트번호),
판정, 불합격 사유. 유형별 합격·불합격 건수 요약도 함께 준다.

**응답은 전체가 아니라 유형별 최신 20건이다.** 두 번 고쳐서 여기까지 왔다.

1. 첫 구현은 전체를 실어 보내고 **화면이** 최신 50건으로 잘랐다. 그랬더니 IQC가 한
   건도 안 남았다 — IQC의 검사일은 자재 입고일이라 늘 PQC·OQC보다 과거다. "세 유형을
   다 기록한다"는 말이 화면에서 거짓이 됐다. 그래서 유형별로 자르게 바꿨다.
2. 그래도 **전체를 실어 보낸 뒤 대부분을 버리는 구조**는 그대로였다(314건 70KB를
   보내고 60건만 씀). 로트와 마찬가지로 기록이 영구히 쌓이므로 응답·파싱 비용이
   기록 수만큼 커진다. PR #9 리뷰 지적을 받아 **상한을 서버로 옮겼다**(13.5KB).

이때 **요약 건수는 잘라낸 기록까지 세야 한다.** 목록만 세면 상한을 걸자마자 합격·
불합격 건수가 조용히 줄어, 화면이 실제보다 적은 검사가 있었다고 말하게 된다. 집계
질의로 세고 회귀 테스트로 고정했다.

대시보드 KPI에는 **넣지 않는다** — KPI는 리스크 지표인데 이번 범위에 완제품 부족
판정도 품질 리스크 판정도 없다.

### 결정 H — 메뉴에 품질관리를 생산과 영업 사이에 넣는다

ERP 단이 6개가 된다(사용자 확인: *"위치 오케이"*): 기준정보관리 → 구매관리 →
재고관리 → 생산관리 → **품질관리** → 영업관리. 자재 입고(IQC) → 생산(PQC) → 출하(OQC)의 흐름 순서이고, 품질관리가 생산과
영업 사이에 오는 것이 OQC가 출하의 관문이라는 결정 C-2와 맞는다. 경로는 `/quality`.

## 6. 알려진 함정

1. **스키마가 바뀌므로 기존 DB는 반드시 재시드해야 한다.** 마이그레이션 도구가 없다.
   로컬 `python -m app.seed`, 도커 `docker compose down -v`. **기록된 리스크 상태는
   사라진다.** README의 같은 경고를 이번 변경에 맞게 갱신한다.
2. **유효기간 파생 전환이 자재 시드를 깬다.** 현재 시드는 유효기간을 입고일과 무관하게
   박아 넣는다(실측: 40일 전 입고 로트에 기준일+4일 만료). 설정기간 파생으로 바꾸면
   **만료 부족 시나리오를 입고일로 다시 만들어야 한다.** 예: 그 자재의 설정기간을
   44일로 두고 40일 전 입고 → 기준일+4일 만료. 잔량 로트는 10일 전 입고 → 기준일+34일.
   기존 회귀 테스트(`test_material_risk.py`, `test_seed.py`)가 이걸 잡아준다.
3. **정상 로트가 대량 만료되지 않게 설정기간을 넉넉히 잡는다.** `_regular_lot_plan`의
   입고일이 5~60일 전이므로 설정기간이 짧으면 멀쩡한 자재가 죄다 만료로 뒤집힌다.
4. **`WAREHOUSES` 이름 변경은 5개 파일을 동시에 고쳐야 한다.** 하나라도 빠지면
   `ImportError`. 변경 후 `grep -rn "WAREHOUSES" backend`로 잔여 참조를 확인한다.
5. **`ck_material_lot_warehouse`가 넓어지지 않았는지 반드시 테스트로 확인한다.**
   상수 하나를 공유하다 분리하는 변경이라 실수가 조용히 통과한다.
6. **SQLite는 기본적으로 FK를 강제하지 않는다.** ~~이번엔 켜지 않고 CHECK 제약 +
   회귀 테스트로 막는다.~~ → **PR #9 리뷰에서 뒤집었다(2026-09-03).** 켜지 않으면
   `ForeignKey` 선언이 문서일 뿐이라, 존재하지 않는 대상을 가리키는 검사 기록이
   저장되고 조회 시 세 관계가 모두 `None` 이 되어 대상 표기 코드가 터진다. 앱을
   통해서는 도달할 수 없지만(쓰기 경로가 시드뿐) 제약이 약속한 것을 지키지
   못한다는 점은 CHECK 제약을 넣은 이유와 같다. `app/db/base.py` 에서 엔진 연결마다
   `PRAGMA foreign_keys=ON` 을 걸고, 켜져 있음과 댕글링 FK 거부를 회귀 테스트로
   고정했다. 전체 테스트는 그대로 통과한다(기존 동작이 바뀔 것이라는 우려는
   근거가 없었다).
7. **`불합격` 사유를 NULL 로만 막으면 빈 문자열이 통과한다.** 같은 리뷰에서 지적됐고,
   빈 사유는 화면에 사유 없는 불합격 행으로 그대로 그려진다. 게다가 **SQLite 의 1인자
   `trim()` 은 공백(0x20)만 지운다** — 탭·개행만 담긴 사유가 그대로 통과한다(실측:
   `trim(char(9)) <> ''` 는 참). 지울 문자를 명시한 2인자 형태로 고쳤다.
8. **한 물리적 로트가 두 창고에 나뉘어 있으면 로트 행이 둘이다.** 행 단위로 무언가를
   만들면 조용히 두 배가 된다(IQC 기록이 그랬다). 기준정보의 보유 로트 수가 이미
   로트번호로 세고 있으니, 새로 만드는 것도 그 단위를 따라야 한다.
9. **완제품 로트와 검사 기록의 수가 많다.** 로트는 5제품 × 과거 30일 ≈ 150개, IQC는
   자재 로트 수만큼, PQC는 생산일 수만큼. `/sales`는 제품별 접기·펼치기로,
   `/quality`는 유형 필터 또는 유형별 섹션으로 나눠야 읽을 수 있다
   (`/materials`의 로트 펼침과 같은 방식).
10. **Codespaces 디스크.** 32GB 루프 디바이스라 `npm run build` 전에 여유를 확인한다
   (`docs/2026-09-02-codespaces-disk-cleanup.md`).
11. **합성 데이터 원칙.** 실제 회사·제품·거래처명을 쓰지 않는다. 불합격 사유도 가상의
   일반적 문구여야 한다.
12. **경로는 그대로 `/sales`.** 라벨만 쓰고 URL은 유지하는 기존 규칙을 따른다
    (실측: `frontend/lib/navigation.ts` 주석). 품질관리는 신규라 `/quality`로 새로 만든다.

## 8. 리뷰에서 받아들이지 않은 지적 (2026-09-03, PR #9 3차)

받아들인 것은 코드에 남으니 여기엔 **기각한 것과 그 이유**를 적는다. 나중에 같은
지적이 오면 다시 판단할 근거가 되도록.

### 기각 ① — 유니코드 공백 전체를 CHECK 제약으로 막으라

> 수직 탭(U+000B), 폼 피드(U+000C), 비분리 공백(U+00A0), 전각 공백(U+3000)만 담긴
> 불합격 사유가 여전히 통과한다.

사실이다. 그러나 **CHECK 제약이 이 일에 맞는 도구가 아니다.** SQLite에는 정규식이
없어 `trim(reason, <문자목록>)` 뿐인데, 유니코드 공백은 25개가 넘고(U+2000–U+200A,
U+2028, U+2029, U+202F, U+205F …) 목록을 늘려도 완전해지지 않는다. 읽을 수 없는
SQL 식만 남고 여전히 빈틈이 있다.

**맞는 자리는 쓰기 경로의 입력 검증이다.** 파이썬 `str.strip()` 은 유니코드 공백을
전부 다루므로, Pydantic 검증기 한 줄이면 완전하다. 그런데 이 저장소에는 검사 기록을
만드는 쓰기 경로가 없다(시드는 고정 문구 상수를 쓴다). 후속 ①(재고이동 = 쓰기 워크플로)
에서 쓰기가 생길 때 그 계층에 넣는다.

지금의 CHECK 는 **사람이나 소박한 임포터가 실제로 만들어 내는 값**(빈 문자열, 공백,
탭, 개행)을 막는다. 마지막 저지선이지 유일한 방어선이 아니다.

### 기각 ② — 완제품 로트 목록에도 응답 상한을 두라

> 검사 이력처럼 `/api/finished-goods` 도 로트를 전부 싣는다.

검사 이력과 **모양은 같지만 성질이 다르다.**

1. **클라이언트가 받은 것을 다 쓴다.** 검사 이력은 314건을 보내고 60건만 썼다(81%
   낭비). 완제품 로트는 모든 행이 화면에 렌더되고, **동시에 다섯 수량의 재료**다.
2. **자르면 화면의 불변식이 깨진다.** "다섯 수량은 서로 겹치지 않으며 합이 로트 합계와
   같다" 는 이 화면이 내세우는 검증 가능한 성질이고 회귀 테스트로 고정돼 있다. 목록을
   자르면 그 합이 맞지 않게 된다.
3. **판정 규칙을 SQL로 복제해야 한다.** 수량을 집계 질의로 내려면
   `_finished_goods_lot_state` 의 우선순위 규칙(만료 → 창고 → 검사 상태)을 CASE 식으로
   옮겨야 한다. 같은 규칙이 두 언어에 살면 갈라진다.
4. **`/materials` 가 같은 모양이다.** 자재도 로트를 전부 실어 `<details>` 로 편다
   (16KB). 완제품만 바꾸면 두 화면이 다른 규칙으로 동작한다.

실측 크기는 28KB로, 상한을 건 검사 이력(13.5KB)이나 자재(16KB)와 같은 자릿수다.

**다만 지적의 전제는 맞다** — 로트는 영구 기록이라 언젠가는 커진다. 지금 안 커지는
이유는 시드가 매번 30일치를 다시 만들기 때문이지 구조 덕분이 아니다. **재검토 시점은
후속 ③(출하 리스크)이다.** 출하가 붙어 로트가 실제로 누적되기 시작하면, 그때
`/materials` 와 함께 두 화면의 로트 목록에 같은 규칙으로 페이지네이션을 넣는다.
