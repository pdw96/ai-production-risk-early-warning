> 열어 놓는 설계 질문뿐이다.

## 출처

2026-09-02 사용자 발화 (원문):

> 창고 구분(원재료 창고, 생산창고, 완제품 창고), 창고 내 이동 시, 예를 들어

## 후속 ① 재고이동 처리 (트랜잭션·이력)

**무엇:** "원재료창고 100EA 로트에서 50EA를 생산창고로 이동" 을 **행위로**
기록하고, 화면에서 처리할 수 있게 한다.

**왜 후속인가 (실측):** 현재 앱의 쓰기 경로는
`PATCH /api/risks/{risk_id}/status` **하나뿐**이다(`backend/app/api/routes.py`).
나머지는 전부 조회다. 프론트도 `updateRiskStatus` 외에 변경 호출이 없다
(`frontend/lib/api.ts`). 즉 이건 기능 추가가 아니라 **쓰기 워크플로 도입**이다.

**열려 있는 설계 질문:**
- 이동을 이벤트 테이블(`StockMovement`)로 적고 로트 잔량을 파생시킬 것인가,
  아니면 로트 잔량을 직접 갱신하고 이력을 따로 남길 것인가
- 이동이 14일 시뮬레이션에 미치는 영향은? (LOT/FIFO 범위의 가정대로 두 창고를
  합산해 가용으로 보면 **총 가용량은 안 변한다** — 그럼 이동 기능의 리스크상
  가치는 무엇인가를 먼저 답해야 한다)
- 되돌리기(취소 이동)가 필요한가
- 합성 데모에서 사용자가 실제로 이동을 눌러 보게 할 것인가, 아니면 이력만 볼 것인가

## 후속 ② 완제품 로트 + 완제품창고

**무엇:** 생산창고에서 생산된 완제품에 LOT을 부여하고 완제품창고로 이동시킨다.

**왜 후속인가 (실측):** 완제품은 `Material` 이 아니라 `Product` 다
(`backend/app/db/models.py`). 현재 `Product` 에 붙어 있는 것은 `Order` 와
`BomRequirement` 뿐이고, **완제품 재고라는 개념 자체가 없다.**
`DailyProduction.actual_quantity` 는 오더별 생산 실적일 뿐 재고가 아니다.

그래서 `MaterialLot.warehouse` 의 값 집합을 `원재료창고`/`생산창고` 둘로 제한하고
완제품창고를 뺐다. 이 선이 이번 범위와 후속을 가르는 경계다.

**열려 있는 설계 질문:**
- `FinishedGoodsLot(product_id, lot_number, quantity, produced_date, warehouse)`
  형태로 갈 것인가
- `DailyProduction.actual_quantity` 와 완제품 로트 수량의 관계는? 실적을 적으면
  로트가 자동 생성되는가, 별개로 입력되는가 (**둘이 어긋날 때 무엇이 진실인가**가
  핵심 질문이다)
- 완제품에도 유효기간/FIFO가 필요한가 (소재 제조업 가정에서는 있을 법하다)
- 출고(출하)로 완제품 로트가 빠지는 규칙은 후속 ③과 같이 설계해야 한다

## 후속 ③ 출하 일정 대비 완제품 부족 판정

**무엇:** 출하 일정과 완제품 재고를 비교해 부족하면 리스크로 올리고 대책을 제시.

**왜 후속인가:** 이건 **세 번째 리스크 타입**이다. 현재
`RiskResponse.risk_type` 은 `Literal["납기", "자재"]` 로 못 박혀 있고
(`backend/app/schemas/contracts.py`), `briefing.list_risks` 도 오더 루프 + 자재
루프 두 개로 하드코딩돼 있다. 프론트 `Risk` 타입도 마찬가지다.

**먼저 답해야 할 질문 — 기존 납기 리스크와 겹친다:**

현재 납기 리스크는 *"오더의 최근 7일 평균 생산량으로 잔여량을 나눈 완료예정일이
납기일보다 늦은가"* 를 본다. 출하 리스크는 *"출하일에 완제품 재고가 충분한가"* 다.
**같은 사건을 두 번 경보할 수 있다.** 예: 오더가 늦어져 완제품이 안 쌓이면
납기 리스크와 출하 리스크가 동시에 뜬다.

그래서 후속 ③ 착수 전에 이걸 정해야 한다:
- 출하 리스크가 납기 리스크를 **대체**하는가(오더 완료 → 완제품 입고 → 출하로
  이어지는 한 줄기로 재설계), 아니면 **공존**하는가
- 공존한다면 중복 경보를 어떻게 묶어 보여줄 것인가
- `Shipment` 엔티티(출하일, 제품, 수량, 거래처)를 새로 만들 것인가.
  거래처는 합성 데이터 원칙상 가상 이름이어야 한다
- "대책 마련" 의 구체적 형태 — 현재 `recommendation` 은 고정 문구 매핑이다.
  출하 부족의 권장 조치도 같은 방식으로 충분한가

## 후속 ④ ERP 모듈의 상세 메뉴(서브메뉴)

**무엇:** 5개 ERP 모듈 안을 상세 메뉴로 나눈다.

**왜 후속인가 (2026-09-02 실측):** 서브메뉴 후보를 실제로 채워 보면 16개 중
**8개가 데이터가 없어 빈 껍데기**가 된다. 내용이 있는 8개 중 5개는 이미 한
화면 안에서 보이는 것을 쪼개는 것이라 클릭만 한 번 늘고 얻는 게 없다.

| 모듈 | 상세 메뉴 후보 | 2026-09-02 기준 상태 |
|---|---|---|
| 기준정보관리 | 품목관리 | 있음 — `/master` 상단 패널 |
| 기준정보관리 | BOM관리 | 있음 — `/master` 하단 패널 |
| 기준정보관리 | 거래처관리 | **없음** — 엔티티 자체가 없다 |
| 구매관리 | 입고예정 | 있음 — `/purchases` |
| 구매관리 | 발주관리 | **없음** |
| 구매관리 | 입고실적 | **없음** — `purchase_receipts` 는 예정만 있고 실적 개념이 없다 |
| 재고관리 | 재고현황 | 있음 — `/materials` |
| 재고관리 | 로트·유효기간 | 있음 — `/materials` 의 로트 펼침 |
| 재고관리 | 창고별 재고 | 있음 — `/materials` 의 창고별 재고 컬럼 |
| 재고관리 | 재고이동 | **없음** — 후속 ① |
| 생산관리 | 생산오더 | 있음 — `/orders` 상단 |
| 생산관리 | 생산실적 | 있음 — `/orders` 하단 패널(2026-09-02 추가) |
| 생산관리 | 설비·품질 | **없음** — README 확장 계획 |
| 영업관리 | 수주관리 | **없음** — 후속 ② |
| 영업관리 | 출하관리 | **없음** — 후속 ③ |
| 영업관리 | 완제품재고 | **없음** — 후속 ② |

**지금 쓰는 방식이 이미 답에 가깝다.** 모듈 페이지 안에서 섹션(패널)으로
나누고, 화면이 늘면 그 섹션을 그대로 서브메뉴로 승격시킨다. 기준정보관리의
`품목 마스터` + `BOM 소요량`, 생산관리의 `생산 오더` + `생산실적`이 그 형태다.

**승격 기준(제안):** 한 모듈에 독립 화면이 **3개 이상** 쌓일 때 서브메뉴로
올린다. 이 기준은 **추정**이며 사용자와 합의되지 않았다.

**착수 조건:** 후속 ①②③ 중 최소 하나가 끝나야 의미가 생긴다. 그 작업들이
어떤 화면을 만드느냐가 서브메뉴 구조를 결정하므로, 먼저 정하면 두 번 고치게
된다.

## 착수 순서 제안 (추정)

② → ③ → ① 순을 권한다.

- ②가 없으면 ③이 성립하지 않는다(완제품 재고가 없으면 출하 부족을 못 잼)
- ①은 ②·③과 독립적이고, LOT/FIFO 범위의 가정(두 창고 합산 가용)대로면
  **총 가용량을 바꾸지 않으므로 리스크 판정에 미치는 영향이 가장 작다.**
  가장 늦게 해도 손해가 없다
- ④(서브메뉴)는 마지막이다. 앞의 셋이 만든 화면을 보고 구조를 정해야 한다

이 순서는 **추정**이며 사용자와 합의되지 않았다.
