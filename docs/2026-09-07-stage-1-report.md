## 설계도와 달라진 자리 넷

설계는 여기까지가 읽는 문서였다. 코드가 그림을 검증하기 시작하면서 넷이 걸렸다.

### ① 공통코드 그룹이 21이 아니라 23이다

34판이 「그룹 스물하나 · 값 고정 열넷 · 값 가변 일곱」이라 적었는데, 값 고정
표에는 **열다섯 줄**이 있다. 그중 `RISK_STATUS` 가 「경보 층과 함께 보류」로
적혀 있어 셈에서 빠진 것으로 읽었다. 이미 `risk_statuses.status` 로 코드에 있는
값이므로 목록에 넣었고, 지적 ㉛이 더한 `UOM` 까지 합쳐 **23**이 됐다.

되돌리려면 `app/core/codes.py` 의 `CODE_GROUPS` 와 `01_common_codes.sql` 에서
해당 줄을 지우면 된다. 다른 결정에 얽혀 있지 않다.

### ② 「계량형 열넷」은 코드의 수이지 항목의 수가 아니다

31판이 계량 코드 14개를 세었는데, 그 코드들이 가리키는 **검사 항목**은 13개다 —
`IQ-COL` 과 `FQ-COL` 이 둘 다 「색차」를 가리키기 때문이다. 검사항목 18개를
맞추기 위해 `IQ-DIM`(치수 이탈 · 두께 · 폭)이 언급한 「폭」을 독립 항목으로 두고
`IQ-DIM` 은 「치수」에 연결했다. **계량 항목 14 · 계수 항목 4 = 18**이 된다.

이것은 읽기이며 사용자와 합의된 것이 아니다. 「폭」을 항목에서 빼면 17이 된다.

### ③ PostgreSQL 이 옮기자마자 값을 냈다

기준정보 SQL 이 불리언 칸에 `1`/`0` 을 넣고 있었다. SQLite 는 그대로 받았고
PostgreSQL 은 거부했다 — 설계도가 「숫자 칸에 글자를 넣으면 그냥 들어간다 ·
거부한다」로 적어 둔 차이가 첫 기동에서 그대로 걸린 것이다.

값을 `TRUE`/`FALSE` 로 고치고, **불리언 칸 목록을 모델 메타데이터에서 뽑아**
검사하는 가드를 두었다(`tests/test_sql_portability.py`). 손으로 적은 목록은 칸이
하나 늘 때 조용히 뒤처진다. 가드가 실제로 실패하는지도 확인했다.

### ④ 자동 생성 마이그레이션이 한 엔진의 문법을 굳혔다

Alembic 자동 생성은 CHECK 제약을 실행 시점 방언으로 구워 **문자열로** 박는다.
불합격 사유의 공백 검사는 SQLite 가 `trim(x, y)` 이고 PostgreSQL 이 `btrim(x, y)`
이므로, 그 문자열이 남으면 다른 엔진에서 규칙이 조용히 사라진다. 8판이 「SQLite
문법으로 고쳤다가 다시 고치면 두 번」이라 적은 자리가 정확히 여기였다.

모델이 쓰는 식(`failure_reason_is_present`)을 마이그레이션이 그대로 부르게 했고,
`migrations/versions/` 에 한 엔진의 문법이 박히는 것을 테스트가 막는다.

## 확인한 것

- **백엔드 198개 · 프론트 60개** 테스트 통과. 프론트는 파일 한 줄도 안 바뀌었다.
- **마이그레이션이 모델과 같은 표를 만든다** — 컬럼 자료형·널 허용·기본키·
  외래키·유일키·CHECK 까지 비교한다(`tests/test_migrations.py`).
- **PostgreSQL 16 에서 실제로 돌렸다** — 마이그레이션 → 시드 → 엔드포인트 12개
  응답 → 재기동 시 시드 건너뛰기.
- **시드가 중간에 터지면 아무것도 남지 않는다** — 일부러 터뜨린 뒤 품목 표가 0
  행이고, 다음 시도가 정상적으로 채운다.
- **기준일 14개**에서 시드의 정합 검사가 모두 통과한다. 기준정보를 고정값으로
  내리면서 난수 시퀀스가 통째로 밀렸기 때문에 확인이 필요했다(정상·주의·위험
  납기 세 상태 · 유효기간 폐기로 부족해지는 자재 · OQC 세 상태 · 두 창고에
  나뉜 로트 · 불량품 재고).

## 하지 않은 것

- **반제품(SF-) 데이터를 넣지 않았다.** 표는 자리를 내주었고 제약도 섰지만
  (`tests/test_models.py::test_a_semi_finished_item_finally_has_a_seat` 가 2단
  BOM 두 줄을 실제로 세운다), 시드에 넣지 않았다. `MasterItemResponse.item_type`
  이 `제품`·`자재` 둘뿐이라 반제품을 넣으면 API 응답 모양이 바뀌고, 그것은
  제약 ①을 깬다. 반제품 오더가 생기는 **5단계(생산 흐름)**의 일이다.
- **완제품 안전재고 값을 정하지 않았다.** 칸은 통합으로 생겼지만 비워 두었다.
  없는 값을 지어내면 화면에서는 있는 것처럼 보인다.
- **조정사유(`ADJ_REASON`) 목록을 비워 두었다.** 실제로 조정을 내 보아야 목록이
  나온다는 17판의 원칙 그대로다. 빈 기준정보는 없는 기준정보보다 나쁘다.
- **σ 를 전부 비워 두었다.** 규격에서 뽑은 σ 는 어떤 계수를 쓰든 Cpk 를 그
  계수의 역수로 못박는다. 경고선과 WE 규칙 4 는 σ 없이 그대로 돈다.
- **화면을 만들지 않았다.** 1단계는 화면이 없는 단계다. 새 표(공통코드 · 거래처 ·
  검사 기준 · 공급사별 품목)는 아직 어떤 API 도 노출하지 않는다.
- **비가동 구간을 시드하지 않았다.** 표는 있지만 구간이 날짜를 가지므로
  기준정보 SQL 에 넣을 수 없다 —「오늘」이 나오면 파이썬이라는 경계 때문이다.
  월말 실사 창을 만드는 것은 실사가 실제로 생기는 단계의 일이다.

## 다음 단계가 읽을 것

2단계는 **관문 1·2(IQC 판정 · 특채 승인 → 자재 재고 로트 생성)**이고, 이
계획의 산이다. 첫 쓰기이며 검사 표 둘(검사 · 검사 측정값 줄)과 수불 원장이
함께 선다.

1단계가 그 앞에 깔아 둔 것:

- 불합격 사유 코드 19개와 **「코드 × 단계」 처분 기본값**이 이미 표에 있다.
  검사원이 코드를 고르면 처분 칸이 채워진다.
- 특채 사유 5개와 단계별 특채 가능 여부가 있다.
- 공정별 검사 기준 23줄이 있다 — 측정값 줄이 생기면 그때의 규격·중심선·경고선을
  기록에 박아 둘 수 있다.
- 수불유형 12개와 총량 영향·짝·근거 문서가 있다. 원장이 설 때 유형을 새로
  정의할 필요가 없다.
- 로트 표에 재고구분과 재작업 칸이 이미 있다.

2단계가 손대야 하는 자리:

- `quality_inspections` 의 `inspected_date` 를 `datetime` 으로 넓힌다(지적 ⑳).
  WE 규칙 넷 중 셋이 점의 순서를 요구한다.
- 검사 측정값 줄을 만든다. 키는 `(검사, 항목, 표본번호)` 다(지적 ⑮ · ㉓).
- 합부를 측정값에서 파생시킨다(지적 ㉔).
- 수불 원장을 만들고, 시드가 만들어 둔 로트를 **「전기이월」 첫 줄**로 깐다.
